### 1.1 飞书同步功能调试

#### 问题 1：FeishuSyncService 缺少条件开关

**症状**：
- 无论 `FEISHU_ENABLED` 设置为 `true` 还是 `false`，Spring 都会尝试创建 `FeishuSyncService` 和 `HttpFeishuOpenApiClient` Bean
- 当 `FeishuProperty` 缺少必要配置时，应用直接崩溃

**错误信息**：
```
Error creating bean with name 'feishuSyncService'
No default constructor found for HttpFeishuOpenApiClient
```

**解决方案**：
1. 给 `HttpFeishuOpenApiClient` 添加 `@ConditionalOnProperty(prefix = "feishu", name = "enabled", havingValue = "true")`
2. 给 `FeishuSyncService` 添加同样的条件注解
3. 在 `InputMessageServiceImpl` 中添加 `@Autowired(required = false)` 和空检查
4. 添加默认构造函数以支持条件创建

**涉及文件**：
- `src/main/java/top/rslly/iot/services/feishu/HttpFeishuOpenApiClient.java`
- `src/main/java/top/rslly/iot/services/FeishuSyncService.java`
- `src/main/java/top/rslly/iot/services/InputMessageServiceImpl.java`

---

#### 问题 2：飞书 Token 获取失败

**症状**：
```
Feishu tenant access token missing in response
```

**原因**：
- 飞书 Token API 返回的数据直接在顶层，不是嵌套在 `data` 字段中

**错误响应**：
```json
{
  "code": 0,
  "tenant_access_token": "t-xxx",
  "expire": 6652
}
```

**代码期望**（错误）：
```json
{
  "code": 0,
  "data": {
    "tenant_access_token": "t-xxx"
  }
}
```

**解决方案**：
修改 `HttpFeishuOpenApiClient.getTenantAccessToken()` 方法，直接从响应顶层读取 token

---

#### 问题 3：飞书文档创建/追加内容失败

**症状**：
```
Feishu append document content failed with httpStatus=400
errorMessage=invalid param
```

**原因分析（通过引入 Lark 官方 SDK 抓包比对得出）**：
1. **API路径不正确**：向文档根节点追加块时，不能使用固定的字符串 `"root"` 作为父节点ID，必须将文档ID本身作为块ID传递。即 `/docx/v1/documents/{documentId}/blocks/{documentId}/children`。
2. **段落对象Key错误**：在飞书 Docx v1 的数据结构中，`block_type = 2` 代表的是“文本（Text）”，因此它的 JSON key 应该是 `text` 而不是 `paragraph`。

**解决方案**：
1. 修改 API 路径构建，将父块ID设为文档ID：`"docx/v1/documents/%s/blocks/%s/children", documentId, documentId`。
2. 修改 JSON Payload，将 `child.put("paragraph", paragraphNode);` 改为 `child.put("text", paragraphNode);`。

**当前状态**：✅ **已修复并测试通过**，飞书鉴权、创建、推送追加全文内容功能彻底打通。

### 5.1 基础设施服务（Docker Compose）

使用 `docker-compose.infra.yml` 启动基础依赖组件：

```bash
cd /opt/IntelliConnect/docker
docker compose -f docker-compose.infra.yml up -d
```

启动的容器服务：

| 服务 | 镜像 | 宿主机端口 | 说明 |
|------|------|-----------|------|
| Redis | `redis:6.2.17` | 6379 | 缓存与会话管理 |
| MySQL | `mysql:8.0` | 3306 | 关系型数据存储 |
| InfluxDB | `influxdb:1.6.4` | 8086 | 时序数据库 |
| EMQX | `emqx:5.8.4` | 1883/18083 | MQTT 消息中间件 |
| ChromaDB | `chromadb/chroma:0.4.24` | **8010**→8000 | 向量数据库（映射 8010 避免与 autossh 隧道冲突） |
| FunASR | `harryliu888/funasr-online-server` | 10095/10096 | 语音识别服务 |

#### 端口冲突处理

由于宿主机已运行 MySQL 和 Redis（宝塔面板管理），有两种处理方式：

- **方式一（当前使用）**：使用 `docker-compose.infra.yml`，其中 MySQL/Redis 端口映射不变（3306/6379），需确保宝塔的 MySQL/Redis 已停止或修改端口。
- **方式二（备选）**：在 `docker-compose.yml` 中修改端口映射为 MySQL `3307:3306`、Redis `6380:6379`，同时修改 `application.yaml` 中的连接端口。

验证容器状态：


#### 5.3.3 Nginx 配置

由于服务器上有宝塔面板管理，在宝塔中新建站点或在现有站点的 Nginx 配置中加入：

```nginx
server {
    listen 80;
    server_name your_domain_or_ip;

    # 前端静态页面
    location / {
        root /opt/IntelliConnect/web/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # 后端 API 反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket 反向代理（实时通信）
    location /ws/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
    }

    # Swagger API 文档（可选，生产环境可关闭）
    location /swagger-ui/ {
        proxy_pass http://127.0.0.1:8080/swagger-ui/;
        proxy_set_header Host $host;
    }
}
```

配置完成后重载 Nginx：

```bash
nginx -t && nginx -s reload
```

### 5.4 LLM 配置要点（2026-03-18 更新）

> G 阶段部署时发现 LLM 配置是最易出错的环节，详见 BUG-001~002。

#### 当前生产配置

LLM 供应商已从 SiliconFlow 切换到**阿里云百炼（DashScope）**：

| 用途 | 配置项 | 模型 |
|------|--------|------|
| 聊天 | `chatTool-llm` | `dashscope-qwen-plus` |
| 情感分析 | `emotionTool-llm` | `dashscope-qwen-plus` |
| 记忆 | `memoryTool-llm` | `dashscope-qwen-plus` |
| 分类器 | `classifierTool-llm` | `dashscope-qwen-max` |
| Agent | `agent-llm` | `dashscope-qwen-max` |
| MCP Agent | `mcp.agent-llm` | `dashscope-qwen-max` |
| AI 内容分析 | 复用 `classifierTool-llm` | `dashscope-qwen-max` |
| 知识图谱 | `knowledge_graphic_llm` | `dashscope-qwen-max` |
| 图片理解 | `vision-model` | `dashscope-qwen-vl-plus` |

#### 注意事项

1. **不要使用 `qwen3.5-plus`**：该模型默认开启思考模式（`enable_thinking`），与 `DeepSeek.java` 通用包装类不兼容，会返回 HTTP 400。使用 `qwen-max`/`qwen-plus`/`qwen-turbo` 替代。
2. **需要思考模式时**：模型名加 `-think` 后缀（如 `dashscope-qwen3-plus-think`），会走 `Qwen3.java` 路径，该类原生支持 thinking 参数。
3. **API Key**：在 `application.yaml` 中配置 `ai.dashscope-key`，当前使用密钥 `sk-ce458d25514a407bae8f1c7f482ad1ea`。
4. **余额监控**：第三方平台余额耗尽是静默失败（HTTP 403 + JSON 错误码），日志中仅显示 `model error`，需查看完整响应定位。

### 5.7 G 阶段部署排障记录（2026-03-18）

G 阶段代码（AI 智能分类、待办提取、知识图谱关联、GitHub 同步）首次部署时发现以下问题，均已修复：

| 编号 | 问题 | 根因 | 修复方式 |
|------|------|------|---------|
| BUG-001 | 所有 AI 功能返回 403 | SiliconFlow 账户余额为零 | 全部 18 个 LLM 配置从 `silicon-*` 迁移到 `dashscope-*` |
| BUG-002 | DashScope 返回 400 `enable_thinking` | `qwen3.5-plus` 默认开启思考模式 | 切换到 `qwen-max`/`qwen-plus`/`qwen-turbo` |
| BUG-003 | AI 分析返回"请提供内容" | AiContentAnalyzer 未发送 user message | 补充 `messages.add(new ModelMessage("user", userPrompt))` |
| BUG-004 | todosJson 保存为 `[{},{},{}]` | fastjson 1.x 不支持 Java record 序列化 | 手动构建 JSONArray 替代 `JSON.toJSONString()` |
| BUG-005 | 每条消息触发 2 次 LLM 调用 | 冗余的 `analyze()` 调用 | 删除多余调用 |
| BUG-006 | 已入库消息无法重新 AI 分析 | 状态机只接受 `received/failed` | 新增 `/reprocess` 端点，支持 `ingested` 消息回退重处理 |

**快速排障表**：

| 症状 | 首先检查 |
|------|---------|
| 所有 AI 功能返回中文兜底消息 | DashScope 余额、API Key 有效性 |
| LLM 返回 400 含 `enable_thinking` | 模型是否默认开启思考模式 |
| AI 分析说"请提供内容" | `messages` 列表是否包含 user message |
| JSON 序列化出 `{}` | 是否在序列化 Java record + fastjson 版本 |
| 一次请求产生两次 LLM 日志 | 检查冗余的 analyze() 调用 |
| 已入库消息无 AI 摘要 | 用 `POST /api/v2/input/messages/{id}/reprocess` 重跑 |
