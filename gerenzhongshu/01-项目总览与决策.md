## 一、项目定位

**个人微信速记与知识归档系统**

主链路：

```
微信收集 → 信息入库 → 分类整理 → 知识归档 → 飞书/GitHub 同步
```

第一优先级功能：

1. 微信消息接入
2. 文本、链接、图片、语音等内容识别
3. 链接抓取正文并转 Markdown
4. 文本速记直接保存
5. 自动分类、标签、待办提取
6. 知识图谱或知识关联
7. 同步飞书文档
8. 同步本地文件与 GitHub

明确不做（当前阶段）：

- 自动改写
- 多平台自动发布
- 工作流编排
- 博主跟踪与运营工作流
- 脱离 IntelliConnect 另起代码线

## 二、底座策略

以 **IntelliConnect v1.0.5**（commit `3a78d7e`）为基础进行**裁剪式二开**。

### 保留清单

| 类别 | 保留内容 |
|------|---------|
| 用户与权限 | 用户体系、登录认证、基础权限、配置管理 |

| MCP/Agent | MCP 配置与服务、角色基础配置、LLM 提供商配置 |
| 微信入口 | 已有控制器和消息回调的可复用部分 |

| 语音硬件 | 硬件语音控制、音频对话、小智硬件耦合功能 |

### 新增清单

| 类别 | 新增内容 |

| 判定 | 模块 | 说明 |

## 三、架构原则

### 3.1 输入层

所有输入源统一走输入层，不把接入协议直接写死到核心业务层。

- 微信采集为第一优先级入口
- 原有输入方式与新增微信采集服务同级接入
- 先标准化消息，再进入归档、标签、同步、待办处理流程

### 3.2 三层架构

| 层级 | 职责 |
|------|------|
| 核心主系统 | 用户、配置、知识库、标签分类、待办、图谱、搜索、同步状态 |
| 输入接入层 | 微信采集、QQ/飞书/Telegram 等后续来源、统一消息标准化 |
| 异步扩展层 | AI 改写、自动发布、自动化流程、重型文件处理 |

### 3.3 先收缩再部署

推荐顺序：

1. 先做功能收缩和边界重组
2. 冻结无关模块，隐藏无关前端入口
3. 跑通最小闭环
4. 本地测试/构建通过后，直接部署到腾讯云环境验证收缩后的版本

### 3.4 上游同步策略

- 保留上游同步分支（`upstream-sync`）
- 新功能优先新增模块实现，尽量少改上游核心公共层
- 前端尽量独立演进
- 合并上游时：先吸收公共层修复，再把分域逻辑重新挂回域层

### 3.5 前端策略

- 前端按业务域拆分（hub / iot）
- 统一登录态、统一入口导航
- 个人中枢和 AI 硬件服务各自保留独立页面心智
- 默认入口优先突出个人中枢

### 3.6 AI 硬件服务并存策略

- 个人中枢主链路是当前 P0
- AI 硬件服务能力并行保留为 P1
- 两者共用底座，通过域分组区分入口/菜单/接口/依赖
- 不做二选一，通过分域和分层方式兼容

## 四、共享层与隔离层边界表

### 一句话原则

**共享公共底座，隔离业务主链路。**

| 层级 | 个人中枢 | AI 硬件服务 | 处理策略 |
|------|----------|-------------|----------|
| 用户认证 | 需要 | 需要 | 共享 |
| 权限模型 | 需要 | 需要 | 共享框架，分域授权 |
| 基础配置 | 需要 | 需要 | 共享框架，分命名空间 |
| 微信输入 | 核心 | 非核心 | 隔离为个人中枢输入层 |
| 设备输入 | 非核心 | 核心 | 隔离为硬件输入层 |
| 知识库 | 核心 | 可选辅助 | 以个人中枢为主，接口可复用 |
| 知识图谱 | 核心 | 可选辅助 | 共享能力，业务对象分离 |
| 速记/待办 | 核心 | 非核心 | 隔离 |
| 设备/物模型 | 非核心 | 核心 | 隔离 |
| OTA | 非核心 | 核心 | 隔离 |
| MQTT/时序 | 非核心 | 核心 | 隔离 |
| 飞书/GitHub 同步 | 核心 | 非核心 | 隔离为个人中枢同步层 |
| MCP/模型接入 | 需要 | 需要 | 共享底座 |
| 前端页面 | 独立前端 | 独立前端 | 分域展示 |
| 统一入口导航 | 需要 | 需要 | 共享 |

### 统一边界口径

- 共享底座，不共享主流程
- 共享认证，不共享业务模型
- 共享配置框架，不混用配置命名空间
- 共享任务框架，不混排任务语义

## 五、核心决策记录

以下为本轮对话确认的 10 条核心决策（精简版）：

| # | 决策 | 结论 |
|---|------|------|
| 1 | 裁剪式二开 vs 全部重写 | 以 IntelliConnect 为基础裁剪式二开 |
| 2 | 当前阶段重点 | 先做个人速记、微信收集、知识归档、同步 |
| 3 | 不用功能处理 | 冻结、隐藏、降级，不立即删除 |
| 4 | 微信接入方式 | 通过独立采集层接入，不写死到主系统 |
| 5 | 前端策略 | 按业务域重构，不沿用旧 IoT 信息架构 |
| 6 | 上游合并 | 保留同步分支，低侵入二开 |
| 7 | 部署顺序 | 先收缩再部署；本地测试/构建通过后直接部署腾讯云，不停留在仅本地验证 |
| 8 | AI 硬件服务 | 并行保留，不替换不删除 |
| 9 | 多前端跳转 | 可行，后端底座统一，前端按域拆分 |
| 10 | 自动化能力 | 后置，通过接口接入，不塞回核心链路 |

## 六、纠偏记录

以下为明确纠偏的 5 条结论：

| # | 偏移 | 纠偏 |
|---|------|------|
| 1 | 错把"新项目独立"推进成"立即新建主代码路线" | `personal-center` 仅为探索性骨架，主工程仍是 IntelliConnect 裁剪式二开 |
| 2 | 错把"代码复用兼容性"当成"当前主路线正确性" | Go 代码兼容只是复用层面，IntelliConnect 才是当前主底座 |
| 3 | 错把 docs 角色降得过低 | gerenzhongshu/ 承担分析和决策留痕，是主执行入口 |
| 4 | 错把"并行能力域"弱化成"后面再说" | AI 硬件服务不是删除，而是并行保留、分域恢复 |
| 5 | 错把探索方案写成默认方案 | 未被本目录确认的新方案只能标为候选或探索性方案 |

一句话纠偏结论：**后面把"新项目独立"过度推进成了"新代码主路线独立"，必须拉回到 IntelliConnect 裁剪式二开主线上。**
