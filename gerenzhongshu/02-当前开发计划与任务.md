## 三·五、部署排障与 Bug 修复记录（2026-03-18）

> G 阶段代码完成后，首次部署到腾讯云测试环境时发现的一系列问题。
> 记录在此便于二开项目日后快速定位同类问题。

### BUG-001: SiliconFlow 余额不足导致所有 AI 功能失效

| 项目 | 内容 |
|------|------|
| **现象** | 所有 LLM 调用返回 HTTP 403，日志 `error code: 30001 balance not enough` |
| **根因** | SiliconFlow 账户余额为零，所有 `silicon-*` 模型（qwen-plus/qwen-max/qwen-turbo 等）全部不可用 |
| **影响范围** | 全局——聊天、分类器、Agent、MCP、天气、音乐等所有 AI 工具 |
| **修复** | `application.yaml` 中 18 个 LLM 配置项从 `silicon-*` 全部迁移到 `dashscope-*`（阿里云百炼），并填入有效的 `dashscope-key` |
| **文件** | `src/main/resources/application.yaml`（约 186-211 行） |
| **教训** | 第三方模型平台余额耗尽是静默失败（HTTP 403 + JSON 错误码），日志里只有 `model error` 一行，需要查看完整响应才能定位 |

### BUG-002: DashScope qwen3.5-plus 思考模式不兼容

| 项目 | 内容 |
|------|------|
| **现象** | 迁移到 DashScope 后，`dashscope-qwen3.5-plus` 返回 HTTP 400：`parameter.enable_thinking must be set to false for non-streaming calls` |
| **根因** | `qwen3.5-plus` 默认开启思考模式（返回 `reasoning_content`），而 `DeepSeek.java` 使用的 `com.unfbx.chatgpt.OpenAiClient` 不支持该扩展字段 |
| **影响范围** | 使用 `DeepSeek.java` 包装类的所有非流式 LLM 调用 |
| **修复** | 将所有模型从 `qwen3.5-plus` 切换到不带默认思考模式的 `qwen-max` / `qwen-plus` / `qwen-turbo` |
| **替代方案** | 如需使用思考模式，模型名需加 `-think` 后缀（如 `dashscope-qwen3-plus-think`），会走 `Qwen3.java` 路径，该类原生支持 thinking 参数 |
| **文件** | `src/main/resources/application.yaml` |
| **教训** | `LLMFactory` 路由逻辑中，`DeepSeek.java` 是通用 OpenAI 兼容包装——名字有误导性；只有 `Qwen3.java` 支持 `enable_thinking` 参数 |

### BUG-003: AiContentAnalyzer 未发送用户消息给 LLM

| 项目 | 内容 |
|------|------|
| **现象** | AI 分析返回 `"请提供需要分析的内容。"`——LLM 收到了 system prompt 但没收到实际内容 |
| **根因** | `DeepSeek.commonChat(String content, List<ModelMessage> messages, boolean search)` 第一个 `content` 参数被完全忽略，只使用 `messages` 列表构建请求。而 `AiContentAnalyzer` 只在 messages 中放了 system prompt，没有放 user message |
| **影响范围** | 所有通过 `AiContentAnalyzer.analyze()` 的 AI 分类/标签/摘要/待办提取 |
| **修复** | `AiContentAnalyzer.java` 第 145 行，增加 `messages.add(new ModelMessage("user", userPrompt))` |
| **文件** | `src/main/java/top/rslly/iot/utility/input/AiContentAnalyzer.java` |
| **教训** | `LLM.commonChat()` 接口设计有陷阱——第一个参数 `content` 名义上是"内容"但实际不被使用。调用方必须自行把 user message 加入 messages 列表 |

### BUG-004: fastjson 1.x 无法序列化 Java record 类型

| 项目 | 内容 |
|------|------|
| **现象** | `todosJson` 字段保存为 `[{},{},{}]`（空对象数组），`todo_item` 表 `content=NULL, priority=NULL` |
| **根因** | `AiContentAnalyzer.TodoItem` 是 Java record 类型，fastjson 1.x 不认识 record 的访问器方法（如 `content()` 而非 `getContent()`），序列化时产生空 JSON 对象 |
| **影响范围** | 待办持久化（`input_message.todos_json` 和 `todo_item` 表均受影响） |
| **修复** | `InputMessageServiceImpl.java` 中将 `JSON.toJSONString(aiResult.todos())` 替换为手动构建 JSONArray（显式调用 `t.content()` 和 `t.priority()`） |
| **文件** | `src/main/java/top/rslly/iot/services/InputMessageServiceImpl.java`（约 694-704 行） |
| **教训** | 项目使用 fastjson 1.x（非 fastjson2），对 Java 17+ record 类型支持不完整。凡是需要序列化 record 的地方，都不能直接用 `JSON.toJSONString()`，必须手动构建或先转为 Map |

### BUG-005: Todo 持久化代码冗余调用 LLM

| 项目 | 内容 |
|------|------|
| **现象** | 每次处理一条消息会调用 2 次 `aiContentAnalyzer.analyze()`（即 2 次 LLM 请求），浪费 token 且增加延迟 |
| **根因** | `InputMessageServiceImpl.java` 约第 735 行有一次多余的 `aiContentAnalyzer.analyze()` 调用，其返回值 `aiResultForTodos` 从未被使用 |
| **影响范围** | 每条消息处理时 token 消耗翻倍 |
| **修复** | 删除冗余的 `aiContentAnalyzer.analyze()` 调用，直接使用上面已序列化好的 `todosJson` |
| **文件** | `src/main/java/top/rslly/iot/services/InputMessageServiceImpl.java`（约 732-737 行） |

### 排障要点速查

| 症状 | 首先检查 |
|------|---------|
| 所有 AI 功能返回中文兜底消息 | SiliconFlow/DashScope 余额、API Key 有效性 |
| LLM 返回 400 含 `enable_thinking` | 模型是否默认开启思考模式，是否走了 `DeepSeek.java` 路径 |
| AI 分析说"请提供内容" | `messages` 列表是否包含 user message |
| JSON 序列化出 `{}` | 是否在序列化 Java record 类型 + fastjson 版本 |
| 一次请求产生两次 LLM 日志 | 检查是否有冗余的 analyze() 调用 |
