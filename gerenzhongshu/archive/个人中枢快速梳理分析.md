# 个人中枢快速梳理分析

> 创建时间：2026-03-09  
> 用途：快速固定当前个人中枢项目的主目标、边界和下一步方案。  
> 说明：本文件独立存在，不替代 `初始需求分析/` 中的历史文档。

---

## 一、当前最核心的目标

当前项目不要再继续优先扩展“自动发布”能力，而是先把个人中枢最基础、最有价值的闭环跑通：

- 微信聊天信息收集
- 个人速记保存
- 自动分类整理
- 知识库归档
- 同步到飞书文档
- 同步到本地文件和 GitHub
- 提取待办事项和知识关联

这条链路跑通后，项目才真正具备“个人数字中枢”的基础价值。

---

## 二、为什么要先收缩范围

原始规划里包含了很多能力：

- 自动改写
- 多平台发布
- 工作流编排
- 博主追踪
- 视频处理
- 多平台账号运营

这些方向并不是错误，而是阶段不对。

如果最基础的“收集 -> 整理 -> 归档 -> 同步”还没有稳定完成，就继续叠加自动发布和自动化流程，只会让系统越来越重，核心价值反而更难落地。

所以当前阶段应明确：

**先做个人信息归档，再做内容运营自动化。**

---

## 三、现在的第一优先级

### 3.1 目标重新定义

把当前项目定义为：

**个人微信速记与知识归档系统**

而不是：

**自动发布平台**

### 3.2 第一优先级功能

必须优先落地的功能：

1. 微信消息接入
2. 文本、链接、图片等内容识别
3. 链接抓取正文并转 Markdown
4. 文本速记直接保存
5. 自动分类、标签、待办提取
6. 知识图谱或知识关联
7. 同步飞书文档
8. 同步本地文件与 GitHub

---

## 四、暂时后置的能力

以下内容先明确后置，不作为当前主开发目标：

- 自动改写
- 自动发布到公众号、小红书、知乎等平台
- 运营型工作流
- 标题钩子优化
- 博主跟踪
- 自动选题扩展
- 面向公域平台的数据分析

这些能力后续可以交给 OpenClaw 或独立自动化服务，通过接口接入，不一定要继续写进当前核心项目。

---

## 五、底座选择的快速判断

### 5.1 轻量项目重做

优点：

- 容易做出轻量 MVP

问题：

- 与当前已有投入衔接成本高

结论：

可作为参考，不适合立刻全面切换。

### 5.2 以 IntelliConnect 为基础做裁剪式二开

这是当前最值得推进的方向。

原因：

- 有知识库、长期记忆、MCP、角色系统等基础
- 有前后端管理能力
- 已经具备微信相关方向的入口

但它的问题也很明显：

- 项目偏 IoT 和设备控制
- 基础设施重
- 有大量与当前 P0 无关的模块

所以正确做法不是原样继承，而是：

**保留知识、记忆、配置、用户、图谱等能力，裁掉 IoT、设备、OTA、MQTT、监控等重模块。**

---

## 六、微信接入的建议

当前你的目标更接近“把微信作为个人信息输入端”，所以最现实的方案是双轨制：

- 短期：网页微信登录方式接入一个辅助微信，用来收集消息
- 中期：预留企业微信或公众号官方接口的替换能力

这里最关键的原则是：

**微信接入必须独立成采集服务，不要把具体协议写死在主系统里。**

这样即使后面网页微信方案不稳定，也只需要替换采集层，不需要重构整个项目。

---

## 七、推荐的新结构

建议后续按下面的结构推进：

### 7.1 主系统

负责：

- 用户和配置
- 知识库存储
- 长期记忆
- 分类和标签
- 待办提取
- 知识图谱
- 飞书和 GitHub 同步

### 7.2 微信采集侧车服务

负责：

- 辅助微信登录
- 消息接收
- 消息标准化
- 调用主系统 API 入库

### 7.3 自动化扩展层

负责：

- 改写
- 发布
- 自动化流程
- 运营任务

这一层后续再交给 OpenClaw 或其他工具处理，不放到当前核心系统里。

---

## 八、接下来最值得做的事

如果按当前思路继续推进，下一步应该是：

1. 先梳理 IntelliConnect 哪些模块保留、哪些模块冻结
2. 单独设计微信采集侧车服务
3. 确认主系统与采集层之间的消息接口
4. 先跑通一条最小链路：微信消息 -> 入库 -> 分类 -> 飞书/GitHub 同步

---

## 九、最终结论

当前项目最需要的不是更复杂的自动化，而是先把个人信息流真正接住。

本阶段的正确顺序应当是：

- 先做微信收集
- 再做速记归档
- 再做分类整理和知识图谱
- 再做飞书与 GitHub 同步
- 最后才考虑自动改写和自动发布

如果要选底座，当前最现实的是：

**以 IntelliConnect 为基础，进行裁剪式二开；以独立微信采集服务补入口；把自动化发布能力放到后期并通过接口隔离。**
