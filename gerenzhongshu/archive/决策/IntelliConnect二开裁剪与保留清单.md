# IntelliConnect 二开裁剪与保留清单

> 创建时间：2026-03-09  
> 用途：明确 IntelliConnect 作为个人中枢底座时，哪些能力保留，哪些模块冻结，哪些内容后期再接。  
> 原则：不是整项目推翻重做，也不是原样继承，而是围绕“个人速记、微信收集、知识归档、同步”做裁剪式二开。

---

## 一、裁剪原则

当前二开的判断标准只有一个：

**是否直接服务于“微信输入 -> 速记归档 -> 知识整理 -> 飞书/GitHub 同步”这条主链路。**

符合这条链路的保留，不符合的冻结或后移。

---

## 二、建议保留的能力

### 2.1 用户与权限

建议保留：

- 用户体系
- 登录认证
- 基础权限控制
- 配置管理

保留原因：

- 这是后台系统的基础能力
- 后续飞书、GitHub、微信接入配置都要依赖用户和配置体系

### 2.2 知识库相关能力

建议保留：

- 知识库存储
- 文档上传和管理能力
- 搜索和召回能力
- 长期记忆相关能力
- 知识图谱相关能力

保留原因：

- 这些能力与个人中枢目标直接一致
- 是从“信息收集”走向“知识沉淀”的核心层

### 2.3 MCP 与角色相关能力

建议保留：

- MCP 相关配置和服务能力
- 角色或 Agent 的基础配置
- LLM 提供商配置

保留原因：

- 后续与 OpenClaw、Claude Code、外部能力接入会用到
- 这些更像平台扩展接口，不必重写

### 2.4 微信现有入口能力

建议保留：

- 现有微信相关控制器和服务的可复用部分
- 已有的消息回调处理思路
- 用户绑定、微信身份映射的可复用逻辑

保留原因：

- 可以减少从零接微信相关业务对象的成本
- 可作为“统一输入层”的一个来源接口

---

## 三、建议冻结的模块

### 3.1 IoT 设备控制主链路

建议冻结：

- 设备控制
- 物模型
- 设备状态监控
- 设备事件处理
- 远程控制

冻结原因：

- 与当前个人中枢目标无关
- 会持续拉高主系统复杂度
- 会干扰接口设计和前端信息架构

### 3.2 OTA 相关模块

建议冻结：

- OTA 升级
- 小智设备 OTA
- 被动 OTA

冻结原因：

- 完全不属于当前阶段的知识归档主线
- 这类模块对部署和运行负担都较重

### 3.3 MQTT / EMQX / 时序数据链路

建议冻结：

- MQTT 通信处理
- EMQX 客户端和 ACL 管理
- InfluxDB 时序数据读写

冻结原因：

- 当前项目不是设备数据平台
- 这些依赖会提高启动复杂度、环境要求和维护成本

### 3.4 语音和硬件链路

建议冻结：

- 硬件语音控制
- 音频对话主链路
- 与小智硬件直接耦合的功能

冻结原因：

- 当前最关键的输入端是微信消息，不是硬件设备语音
- 语音链路对资源和依赖的要求高，应该等主链路稳定后再决定是否恢复

---

## 四、建议后期再接的能力

### 4.1 自动改写

原因：

- 它属于知识内容产出层，不是第一层能力
- 适合通过 OpenClaw 或独立服务接入

### 4.2 自动发布

原因：

- 它是运营动作，不应污染当前知识归档核心系统
- 更适合单独做适配器或外部自动化服务

### 4.3 工作流编排

原因：

- 当前没有必要把 N8N 式流程引擎重新塞进主项目
- 后期可以通过 webhook、队列、OpenClaw Agent 方式来实现

---

## 五、建议新增但独立实现的部分

### 5.1 微信采集侧车服务

职责：

- 辅助微信登录
- 消息拉取或接收
- 消息标准化
- 调用主系统 API 入库

为什么不直接写进主系统：

- 微信接入协议变化快
- 登录态和风控风险高
- 主系统应该只关心标准化后的消息，不关心底层协议

### 5.2 同步适配层

职责：

- 飞书同步
- GitHub 同步
- 本地文件归档

说明：

- 可以挂在主系统里，但要保持适配器化，避免同步逻辑扩散到业务层

### 5.3 新前端信息中枢界面

职责：

- 信息收集流展示
- 速记条目列表
- 知识归档状态
- 同步状态
- 待办与知识图谱入口

说明：

- 这部分不建议继续完全沿用 IntelliConnect 当前偏 IoT 的页面结构

## 七、建议的目录和职责边界

### 6.1 主系统保留区

- 配置
- 知识库
- 记忆
- 图谱
- 搜索

### 6.2 主系统冻结区

冻结方向：

- 物模型
- 时序数据
- MQTT

### 6.3 独立输入层

新增方向：

- 微信采集服务
- 后续 QQ / 飞书 / Telegram 输入源

### 6.4 外部扩展层

后期方向：

- OpenClaw 自动改写
- 发布流程

## 七、执行建议

推荐按下面顺序推进：

1. 先做模块冻结清单和菜单隐藏
2. 再做统一输入层接口定义
3. 然后做微信采集侧车服务
4. 跑通入库、分类、同步主链路
5. 最后再重做适合个人中枢的新前端页面

---

## 八、结论

IntelliConnect 可以作为个人中枢二开的底座，但只能按“保留知识能力、冻结 IoT 主链路、独立输入层、后置自动化扩展”这条路线推进。

如果不先裁剪，后面会出现两个问题：

- 一边做个人中枢，一边继续被 IoT 结构牵着走
- 后续上游更新虽然能合，但冲突和理解成本会越来越高

所以当前最合理的策略不是“大改”，而是：

**先裁剪出一个能承载个人中枢的干净核心。**
