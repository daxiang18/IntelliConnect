# 原项目架构与性能优化建议

> 创建时间：2026-03-09  
> 对象：IntelliConnect 当前架构，重点从“是否适合作为个人中枢底座”这个角度分析。  
> 目标：说明为什么现有架构性能和结构上不够合理，并给出更适合当前阶段的演进建议。

---

## 一、先说结论

IntelliConnect 当前架构不是不能用，而是：

- 对原作者的 AIoT 平台目标来说，功能很全
- 但对你当前“个人速记 + 微信收集 + 知识归档”的目标来说，明显偏重、偏杂、偏耦合

最大的问题不只是“性能慢”，而是：

- 运行边界不清
- 热路径和冷路径混在一起
- 基础设施依赖过多
- 单体服务承担了太多完全不同的职责

所以真正合理的建议不是“直接微服务化”，而是：

**先做模块化单体瘦身，再把输入层和异步耗时层拆出去。**

---

## 二、当前架构为什么显得不合理

根据现有项目结构和配置，可以看到几个明显问题。

### 2.1 依赖过重

当前后端同时引入或启用了：

- Spring Web
- WebSocket
- JPA + MySQL
- Redis
- InfluxDB
- MQTT
- gRPC
- MCP Spring MVC
- Selenium
- 邮件
- Thymeleaf
- ChromaDB（向量存储，通过 langchain4j-chroma）
- 异步任务
- 定时任务

这意味着一个进程里同时承担：

- 管理后台
- 实时通信
- 设备控制
- 时序数据处理
- AI 请求
- 微信入口
- 知识库
- MCP 服务
- 语音和文件处理

问题在于，这些能力的资源特征完全不同。

例如：

- 微信消息接入是轻量 HTTP 回调或消息处理
- 知识库搜索偏数据库和索引查询
- AI 请求偏外部网络等待
- Selenium 偏重浏览器自动化和高资源占用
- OTA 和文件服务偏 IO
- MQTT 和设备控制偏长连接与状态维护

把这些放在一个 JVM 进程里，不是“功能丰富”，而是“竞争资源”。

### 2.2 热路径和冷路径没有分开

对个人中枢来说，真正的热路径应该是：

- 接收消息
- 类型识别
- 存储笔记
- 搜索和查看
- 同步状态回写

但当前结构把很多冷路径也塞进同一个主服务：

- OTA
- 设备数据读取
- 时序查询
- 硬件控制
- 音频流式控制
- 大量设备相关接口

这会带来两个问题：

1. 启动负担重
2. 主链路的稳定性受无关模块拖累

### 2.3 控制器和服务边界过宽

从当前入口可以看出，一个控制器下挂了大量完全不同的服务依赖。

这说明当前更接近“功能堆叠式单体”，而不是“边界清晰的模块化单体”。

风险包括：

- 改一个模块容易影响其他模块
- 权限校验和业务逻辑重复分散
- 后续做裁剪时很难低成本剥离

### 2.4 数据层存在多种存储模型混用

当前项目涉及：

- MySQL 结构化数据
- Redis 缓存
- InfluxDB 时序数据
- 可能还有文件系统和音频临时文件

问题不在于“不能多存储”，而在于当前目标已经变了。

对个人中枢 P0 来说，保留这么多存储后端并不划算，因为：

- 环境搭建成本高
- 调试和迁移成本高
- 备份恢复复杂
- 单机运行门槛高

### 2.5 前后端信息架构不匹配

当前前端页面大量围绕：

- product
- device
- event
- ota
- monitor
- skills
- mcp

而你真正需要的是：

- 收集箱
- 速记箱
- 归档库
- 待办
- 知识图谱
- 同步状态
- 输入源管理

这不是简单换几张页面皮肤能解决的问题，而是前端产品模型本身不同。

## 三、如果继续沿用原架构，会出现什么后果

### 3.1 开发效率下降

因为你每次开发个人中枢能力，都得先绕开 IoT 和设备语义。

### 3.2 性能问题会被放大

不是因为 Spring Boot 本身不行，而是因为：

- 同一进程职责过多
- 无关模块占用内存、线程和连接池
- 外部依赖过多导致整体稳定性变差

### 3.3 上游同步越来越难

如果你在原项目核心文件里大面积混入个人中枢逻辑，后面上游升级时：

- 很多 merge 虽然技术上能做
- 但语义冲突会越来越多

---

## 四、什么样的架构才更合理

### 4.1 不是立即微服务，而是先做三层瘦身

当前阶段最合理的架构不是一步拆成很多服务，而是先把系统整理成三层：

#### 第一层：核心主系统

只保留：

- 用户
- 配置
- 知识库存储
- 标签分类
- 待办提取
- 知识图谱
- 搜索
- 同步状态

特征：

- 这是最核心、最稳定的一层
- 应该尽量轻

#### 第二层：输入接入层

包括：

- 微信采集服务
- 未来 QQ / 飞书 / Telegram 输入接口
- 原项目已有的微信入口适配

特征：

- 统一做消息接入和标准化
- 不把协议细节塞进主系统

#### 第三层：异步扩展层

包括：

- AI 改写
- 自动发布
- 自动化流程
- 重型文件处理
- 浏览器自动化

特征：

- 可以慢
- 可以失败重试
- 不应该拖慢主系统

### 4.2 存储建议要做减法

如果目标是 P0 尽快落地，建议优先保留：

- MySQL 或 PostgreSQL 二选一作为主业务库
- Redis 仅保留必要缓存和会话能力
- 文件系统或对象存储用于原始文件和 Markdown 归档

建议暂时冻结：

- InfluxDB
- 与设备时序相关的专用存储

原因：

- 它们不服务于当前个人中枢核心主线

### 4.3 接口建议统一成“输入消息模型”

当前个人中枢真正应该围绕一个统一实体建模：

- 来源
- 用户
- 会话
- 内容类型
- 原始正文
- 附件
- 元数据
- 归档状态
- 同步状态

这样不管来源是：

- 微信
- 飞书
- QQ
- 未来网页表单

后面都走同一条入库和处理链。

### 4.4 异步化只放耗时任务

当前最适合异步化的任务是：

- 抓取正文
- OCR
- AI 分类或总结
- 飞书同步
- GitHub 同步
- 图谱重建

而不是把整个系统的所有东西都开成异步。

合理做法是：

- 用户请求先快速落库
- 耗时操作通过任务队列或任务表异步处理
- 前端展示处理中状态

这比把所有逻辑直接塞进同步请求里更稳。

## 五、对性能最有价值的改造顺序

### 第一阶段：先减依赖

目标：

- 让核心主系统只承载当前 P0 需要的能力

要做的事：

- 冻结 MQTT、OTA、设备控制、InfluxDB 等链路
- 隐藏无关前端菜单和页面
- 收紧配置项，减少必须启动的外部依赖

### 第二阶段：拆输入层

目标：

- 把微信采集和主系统解耦

要做的事：

- 新增独立微信采集服务
- 统一消息接入 API
- 主系统只接标准化消息

### 第三阶段：拆异步耗时层

目标：

- 把抓取、同步、AI 分类等重任务从主请求里拿出去

要做的事：

- 增加任务表或轻量队列
- 主链路先写入原始记录
- 后台 worker 再处理抓取、总结、同步

### 第四阶段：重做前端信息架构

目标：

- 让前端和个人中枢目标一致

要做的事：

- 新建收集箱
- 新建速记箱
- 新建归档库
- 新建同步状态页
- 把设备导向的旧页面降级或隐藏

---

## 六、关于“是否还能持续合并上游更新”的建议

可以，但前提是二开方式要克制。

建议做法：

1. 上游同步分支单独保留
2. 个人中枢主开发分支单独维护
3. 新需求尽量新增模块，不大改上游核心公共层
4. 前端尽量新建自己的信息中枢页面，不在旧页面上大面积重写

这样以后上游更新时，至少还能做到：

- 核心依赖升级可跟
- 部分功能修复可挑拣合并
- 不至于每次更新都全量人工冲突

---

## 七、最终建议

从你的目标出发，更合理的路线不是：

- 继续在一个重型 AIoT 单体里叠加个人中枢能力

而是：

- 把 IntelliConnect 当作“知识和配置能力底座”
- 把微信采集做成独立输入层
- 把抓取、同步、AI 处理做成异步扩展层
- 把前端改成真正服务于“信息接入和知识归档”的结构

如果只给一个最直接的架构建议，就是：

**不要先追求把系统拆得很大，而要先把当前这个大单体缩成一个轻核心。**

这一步做对了，性能、稳定性、开发效率、后续合并上游更新的可行性，都会一起变好。
