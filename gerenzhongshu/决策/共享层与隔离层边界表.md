# 共享层与隔离层边界表

> 创建时间：2026-03-09  
> 用途：明确“个人中枢”和“AI 硬件服务”并行存在时，哪些能力应该共享，哪些能力必须隔离。  
> 当前说明：本文件作为边界参考文档保留。个人中枢目录入口见 [README.md](README.md)，当前个人中枢边界口径已并入 [项目约束与实施原则.md](项目约束与实施原则.md)。

---

## 一、先看结论

当前最合理的结构不是把两个业务做成完全独立的两套系统，也不是继续塞进一个混乱的大单体里，而是：

- 底座共享
- 业务域隔离
- 前端分域
- 配置分组
- 部署可分环境启用

一句话概括：

**共享公共底座，隔离业务主链路。**

---

## 二、业务域定义

### 2.1 个人中枢域

负责：

- 微信信息收集
- 个人速记
- 知识归档
- 分类和标签
- 待办提取
- 知识图谱
- 飞书和 GitHub 同步

### 2.2 AI 硬件服务域

负责：

- 设备接入与控制
- 物模型
- 语音交互
- OTA 升级
- 设备监控
- 事件与时序数据

---

## 三、应该共享的层

### 3.1 用户与认证层

建议共享：

- 用户账号
- 登录认证
- Token/JWT
- 基础角色权限框架

原因：

- 两个业务域都需要统一身份体系
- 统一登录可以降低系统复杂度

注意：

- 角色权限要支持按业务域细分，不要只有一套粗粒度角色

### 3.2 基础配置中心

建议共享：

- 系统级配置
- LLM 提供商配置
- 基础环境配置
- 同步类公共密钥配置框架

原因：

- 这些属于平台级公共能力

注意：

- 配置要分命名空间，不能把个人中枢配置和硬件配置混成一张平面表

### 3.3 通用存储与公共基础设施抽象

建议共享：

- 主业务数据库接入层
- 公共日志与审计能力
- 文件存储抽象
- 基础任务表或任务框架

原因：

- 这些是底层支撑，不属于某个单独业务域

### 3.4 MCP / Agent / 模型接入底座

建议共享：

- MCP 服务能力
- 模型供应商适配层
- Agent 基础配置

原因：

- 个人中枢和 AI 硬件服务都可能需要调用模型和工具能力

---

## 四、必须隔离的层

### 4.1 输入主链路

必须隔离：

- 个人中枢输入层
- 硬件设备输入层

个人中枢输入层包括：

- 微信采集服务
- 原有消息入口
- 后续 QQ / 飞书 / Telegram 输入源

AI 硬件服务输入层包括：

- 设备上报
- 语音流
- MQTT 消息
- 设备事件

原因：

- 两类输入的协议、延迟、数据形态完全不同
- 不能让一个输入链路污染另一个业务链路

### 4.2 核心业务模型

必须隔离：

- 个人中枢的“消息、笔记、知识条目、待办、同步状态”模型
- 硬件服务的“设备、物模型、事件、OTA、状态、时序”模型

原因：

- 它们不是同一类业务对象
- 不应为了复用而强行共用表结构或语义

### 4.3 前端信息架构

必须隔离：

- 个人中枢前端
- AI 硬件服务前端

原因：

- 页面心智不同
- 操作目标不同
- 菜单结构不同

建议：

- 允许多个前端互相跳转
- 统一登录，但分开页面体系

### 4.4 部署依赖

必须隔离：

- 个人中枢环境不应默认强依赖 MQTT、InfluxDB、OTA 链路
- AI 硬件服务环境不应被个人中枢同步链路牵着走

原因：

- 否则一个域的依赖故障会拖垮另一个域

---

## 五、建议共享但要分组管理的层

这些层不是完全共享，也不是完全隔离，而是：共享底座，分组管理。

### 5.1 权限层

建议：

- 统一认证
- 分业务域授权

示例：

- `hub:collect`
- `hub:knowledge`
- `iot:device`
- `iot:ota`

### 5.2 配置层

建议：

- 统一配置中心
- 分命名空间保存

示例：

- `hub.wechat.*`
- `hub.sync.*`
- `iot.mqtt.*`
- `iot.ota.*`

### 5.3 任务系统

建议：

- 统一任务框架
- 任务类型隔离

示例：

- 个人中枢任务：抓取正文、标签提取、同步飞书、同步 GitHub
- 硬件任务：设备同步、OTA 发布、状态巡检、告警处理

## 六、边界表

| 层级 | 个人中枢 | AI 硬件服务 | 处理策略 |
|------|----------|-------------|----------|
| 用户认证 | 需要 | 需要 | 共享 |
| 权限模型 | 需要 | 需要 | 共享框架，分域授权 |
| 基础配置 | 需要 | 需要 | 共享框架，分命名空间 |
| 微信输入 | 核心 | 非核心 | 隔离为个人中枢输入层 |
| 设备输入 | 非核心 | 核心 | 隔离为硬件输入层 |
| 知识库 | 核心 | 可选辅助 | 以个人中枢为主，接口可复用 |
| 知识图谱 | 核心 | 可选辅助 | 共享能力，业务对象分离 |
| 速记/待办 | 核心 | 非核心 | 隔离 |
| 设备/物模型 | 非核心 | 核心 | 隔离 |
| OTA | 非核心 | 核心 | 隔离 |
| MQTT/时序 | 非核心 | 核心 | 隔离 |
| 飞书/GitHub 同步 | 核心 | 非核心 | 隔离为个人中枢同步层 |
| MCP/模型接入 | 需要 | 需要 | 共享底座 |
| 前端页面 | 独立前端 | 独立前端 | 分域展示 |
| 统一入口导航 | 需要 | 需要 | 共享 |

## 七、开发时最重要的约束

### 7.1 不要改坏共享底座

高风险共享层包括：

- 用户认证
- 公共配置
- 基础数据访问层
- 模型接入层

这些地方要优先做兼容式修改，不做破坏式修改。

### 7.2 不要把一个域的语义塞进另一个域

例如：

- 不要把“设备状态”当成“知识条目”建模
- 不要把“微信速记消息”硬复用为“设备事件”模型

### 7.3 前端分开，不代表后端重复实现

前端可以两套，但：

- 统一登录
- 统一公共 API 网关
- 统一配置中心

不要因为前端分开，就把后端也复制两套。

---

## 八、推荐实施顺序

1. 先确认共享底座范围：认证、配置、模型接入、基础存储
2. 再确认个人中枢隔离层：输入、知识、同步、速记、待办
3. 再确认 AI 硬件隔离层：设备、OTA、MQTT、时序、控制
4. 最后做前端分域和统一导航

---

## 九、最终结论

如果后续继续开发，最应该记住的不是“哪些功能要做”，而是“哪些层不能混”。

当前最合理的边界是：

- 底座共享
- 输入隔离
- 业务模型隔离
- 前端分域
- 部署依赖按域启用

如果只保留一句执行结论，就是：

**共享平台能力，不共享业务混乱。**
